# Наблюдения по реестру органов по оценке соответствия

Источник: [карточка реестра №36](https://tech.eaeunion.org/tech/ru/registers/36), публичный REST `/spd/find`. Проверка 30.09.2026, по 1–2 записи на запрос. Коллекция `kbdread.service-prop-36-v_conformityAssessmentBodyInformationDetailsType_organization_table`.

Проверены фильтры `conformityAuthorityId`, `unifiedCountryCode.value`, `conformityAssessmentBodyDetails.businessEntityUnitName` с `$regex`, `statusV2Details.statusCode.value` и `accreditationCertificateDetails.statusV2Details.statusCode.value`. Для `BY579` и `26490` возвращалось по одной записи; глобальная уникальность идентификатора этим не доказана. Поэтому поиск по ID обрабатывает 0 и несколько совпадений явно.

Страна — объект с полями `value` и `codeListId`, а не одна строка. `_id` представлен как `{"$oid":"…"}`, даты аттестата как `{"$date":"2020-01-01T00:00:00Z"}`. Код статуса — вложенное строковое `value`; `codeListId` иногда отсутствует. Значения статусов записи и аккредитации независимы: наблюдалась запись с `02` и аккредитацией `04`, а также запись с `01` и аккредитацией `02`. Смысл этих кодов и полный список значений из одной выборки не выводим.

Встречались пустые и непустые массивы адресов, должностных лиц и областей аккредитации. Имена органов и юридических лиц лежат в разных объектах. В таблице сайта для `BY579` те же идентификатор, название, аттестат, даты и область, что в REST-записи. Отдельная подробная карточка не открылась при выборе строки таблицы, поэтому полнота REST относительно отдельного представления не подтверждена.

`conformity/testdata/records.json` — синтетические записи по наблюдавшейся схеме; они не содержат реальных контактов или имён. Эти фикстуры проверяют отсутствие необязательных полей, разные страны, статусы, вложенные массивы и сохранение нового поля.
